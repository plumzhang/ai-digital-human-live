# 数字人直播中控台

Windows 桌面客户端，使用 Tauri 2 + React、Vidu S2-Avatar **组件版**、本地 FunASR 中文 ASR、WSL2 OmniVoice 声音克隆（FlashInfer + CUDA Graph）和 [douyinLive](https://github.com/jwwsjlm/douyinLive)。

当前链路：麦克风 → VAD 分句 → FunASR /api/stt → 自己的 LLM 流式回答 → 按句合成克隆语音 → 24kHz / 单声道 / s16le PCM → Vidu WebSocket → 托管阿里 RTC → OBS 播放窗口。弹幕、礼物和手动提问直接进入 LLM。Vidu 不负责识别、回答或合成声音。

## 安装与开发

需要 Windows、Node.js 20+、Rust MSVC、Visual Studio C++ Build Tools、WebView2；语音服务需要 WSL2 和 NVIDIA CUDA GPU。

```powershell
npm install
npm run setup:speech
npm run dev:desktop


```

安装器创建独立的 Ubuntu 24.04 WSL2 发行版 InnoTechx-Speech，保留 Docker 环境。FunASR 在 CPU 环境运行，OmniVoice 在独立 CUDA 12.8 环境运行。需要可用的 WSL2 和 NVIDIA GPU；启动时执行实际推理，验证 FlashInfer + CUDA Graph 后才报告就绪。环境与模型不修改系统 Python。首次安装需下载数 GB 模型和依赖。

统一基础地址为 http://127.0.0.1:8766：

| 接口 | 功能 |
| --- | --- |
| POST /api/stt | FunASR Paraformer 中文识别，返回文字和毫秒时间戳 |
| POST /api/tts | OmniVoice 参考录音声音克隆，返回24kHz单声道s16le PCM |
| POST /api/tts/cancel | 按回答 request_id 取消当前与排队句子 |
| GET /health | 模型、设备和实际加速验证状态 |

## 配置与使用

1. “模型配置 → 大语言模型”：保存 OpenAI 兼容地址、Key、模型和回复规则。模型必须支持 Chat Completions SSE。旧版默认提问优化规则会迁移为主播回答规则；自定义规则保留，请检查其中是否仍要求“只优化提问”。
2. “模型配置 → OmniVoice 语音”或“音色克隆”：保存参考录音的 Windows 绝对路径和对应原话，点击“启动本机服务”，待 FunASR、FlashInfer、CUDA Graph 显示已就绪/已验证后生成克隆试听。软件自动将 C:/G: 等本机路径映射到 WSL2。原 Qwen 配置中的参考路径和原话会保留，新服务固定使用 k2-fsa/OmniVoice。关闭本机服务可在加载、试听或播报期间停止 Linux 进程组并释放显存，同时暂停自动回答和麦克风；未完成播报保留人工确认。
3. “模型配置 → Vidu数字人”：填写 Vidu API Key；“形象设定”保存形象和当前主播人设。旧版音色及高级设置留在存储中，组件版不再使用这些参数。
4. “直播中控”启动数字人。创建前检查 TTS 服务和所选模型；使用 managed_rtc artc 继续订阅音视频，无需自建 RTC。
5. 开启自动回答后处理弹幕和礼物；手动提问在当前播报结束后优先执行。“开启麦克风识别”只采集本地音频，FunASR 通过本机 /api/stt 识别，不向 RTC 发布麦克风。用户开口即打断旧回答，句尾静音约900毫秒后识别并回答。
6. OBS 添加“窗口采集”，选择“数字人画面 · OBS 窗口”，并捕获该应用音频。字幕显示实际送入 TTS 的台词。弹幕 PCM 按槽位设置分别发送给 Vidu、在 OBS 窗口本地播放，无需等待 RTC 下行音频。槽位默认启用 FunASR 本地播报确认：全部 PCM 已发送且本地播放后，识别本地实际播放声音，回答结尾匹配达标且最后3字一致即完成；音视频健康仍需满足，断流或识别失败保留人工确认。

“互动任务队列 → 槽位播放设置”依次包含承接动作、弹幕PCM发送延迟、本地弹幕PCM播放延迟、独立的回复动作区域。承接动作延迟与回复动作延迟分别设置、分别保存，范围均为0–60000毫秒；发送与播放延迟范围均为0–10000毫秒，默认0。修改从下一槽位生效，重启后保留。所有延迟统一从当前槽位进入播放状态开始计时，不累加。例如发送500、播放800，表示槽位开始后约500毫秒发送、800毫秒播放；本地声音可独立于上行发送先后播放。

手动提问和麦克风回答逐句流水执行：每句内部先完成合成，播放当前句时准备下一句。弹幕与礼物槽位提前生成回答，TTS 空闲时按句预合成整条回答的 PCM，轮到该槽位才发送缓存音频。单句内部并非原生 token 级音频流式。

也可运行 npm run start:speech。应用管理的服务随应用退出释放；终端启动的服务可在软件中显式关闭。启停只作用于经过 PID、启动时间和命令行核实的语音进程组，不终止整个 WSL 发行版。Windows 配置和日志位于 %LOCALAPPDATA%/com.innotechx.digitalhuman.live/speech；WSL 环境和模型位于 /opt/innotechx-speech。setup:tts / start:tts 为新语音服务的兼容命令。

## 抖音弹幕采集

“连接抖音弹幕”使用 jwwsjlm/douyinLive v2.3.2，可输入直播间号、live.douyin.com 网页直播间链接，或 webcast.amemv.com/douyin/webcast/reflow/ 手机端直播分享链接。手机分享页面中的长房间 ID 不直接当作网页直播间号，先读取页面的 webRid 再连接；设备和分享追踪参数不参与解析。客户端启动独立 Windows 采集程序，以本地签名模式采集，通过原生 WebSocket 接收消息，再沿用弹幕过滤、礼物连击合并和三槽位队列。消息、用户和礼物分组 ID 按字符串保留，避免大整数精度丢失。未开播或状态暂不确定时保留连接并等待采集服务重试；房间无效、采集失败或连接断开会显示原因，可重新连接。

开发脚本自动准备运行文件；也可先运行 npm run prepare:douyin。版本、来源和 SHA-256 固定在 vendor/douyin-live/release.json，安装包包含 douyinLive.exe 和 MIT LICENSE，不再打包旧 dyhub/Node 采集运行时。运行时选择空闲端口，使用随机认证密钥，仅停止客户端自己启动的采集进程；停止采集和关闭主窗口时释放它。

采集配置与日志位于 %LOCALAPPDATA%/com.innotechx.digitalhuman.live/douyin-live/ 下的 config.yaml、service.log。如抖音要求登录态，可在配置的 cookie.douyin 中填写本机 Cookie 后重新启动采集。历史弹幕和队列继续使用原存储目录，已有数据可继续读取。接入及验证记录见 [douyinLive 接入说明](docs/douyin-live.md)。

## 互动队列与唱歌

使用固定三槽位队列，保留持久化、过滤、手动测试、承接动作及多数字人卡片。槽位1是当前任务，槽位2、3提前准备回答和PCM；已入槽内容不因超过30秒、新弹幕或新礼物自动替换。仅采集弹幕时不会自动跳过，只有播报完成或手动跳过才前移，并从最新未处理弹幕补位。同一秒内按最新接收顺序选择；礼物在候选补位时优先，不挤占已有槽位。候选弹幕超过30秒淘汰，候选礼物保留；旧六槽位的多余任务转入候选，保留礼物和歌曲。手动点击“加入播放歌曲槽位”可替换槽位3的原待播任务，保留槽位1、2；被替换任务记为跳过并释放PCM，不重新放回候选池。不足三条时，歌曲排在现有队尾。“测试输入弹幕”每次仅接受1条弹幕或礼物，同样替换槽位3并清理旧PCM；可在数字人启动、播报及实时采集期间插入，不清空队列、不重置直播间，也不切换当前自动回答开关。弹幕由模型判断动作意图，普通问题默认看向镜头，明确动作请求生成对应描述。每个组件槽位包含承接动作和回复动作：槽位开始先提交承接动作，确认写入后立即发送缓存PCM，再按“回复动作延迟”提交回复动作。两种动作各自发送 type=97 动作提示词与 type=9 动作驱动文本，确认两条均写入连接后显示“已发送”。

“回复动作延迟”与PCM发送、本地播放共用槽位切换起点：0毫秒表示槽位开始时提交回复动作，500毫秒表示槽位开始后500毫秒提交，可设置0–60000毫秒。配置保存到本机，已开始的槽位使用启动时的配置；后续槽位使用新配置。下一槽位开始前不再等待原承接间隔。打断、换会话或上行与本地音频均结束时，尚未触发的回复动作取消。

后台最多并行准备两条回答，OmniVoice 只运行一个合成任务；当前槽位发送 PCM 时，后续槽位仍继续准备。槽位提前显示回答及“正在预合成声音 / 声音就绪”状态，播放时复用 PCM，不再调用模型或 TTS。跳过、重新生成、切换会话和修改音色会清理对应缓存；PCM 只保存在本机内存，重启后重新合成。

回答进入TTS前检查最近已播及已生成回答的开头，并发结果在写入队列时再次检查。“哎呀／哎哟／哎呦”等近似叹词、只换昵称或标点的重复开场会触发LLM重写，保留原问题、礼物信息和动作。待播旧回答若重复则先清理PCM再重写，界面显示“开头重复，正在重写回答”；连续重写仍重复时显示失败，避免反复合成和播放。

“播报结束匹配度”默认70%，可在空闲时调整为50–100%。15字及以上的回答比较末尾10字，更短的回答比较全文；统一忽略标点并兼容同音字，最后3字（短于3字则整句）须完全匹配。识别结果还须属于当前槽位、当前采集，且采集时间不早于PCM发送完成及最近发声。确认结尾后不再额外等待1.5秒或1.2秒静音，立即进入下一就绪槽位的动作与音频流程。

新建歌曲由FunASR转录、LLM校正歌词后，使用本机 Demucs 分离人声与伴奏，再按歌词原始起止时间截取24kHz单声道s16le人声PCM。旧歌曲先点击“分离人声与伴奏”，同时重建人声PCM；原歌曲保留，两条分离音轨可独立试听。歌曲固定在槽位1时，OBS按原时间完整播放伴奏，人声PCM每20毫秒发送给Vidu，声音由RTC下行人声播放。间奏弹幕同样播放RTC返回的声音并用FunASR确认，禁止同时播放本地回复PCM；歌曲结束后恢复普通回复的本地PCM播放。自动回答开启时，槽位2、3继续作为弹幕子队列；下一段唱词优先打断弹幕，唱词期间只执行明确动作与礼物手势。发送提前的人声不会在该句伴奏尚未结束时提前释放通道。RTC音频未订阅时不启动歌曲，断流时停止伴奏并保留人工确认。

提前量设置位于“唱歌模块 → 已有歌曲导播 → 编辑 → PCM提前量（毫秒）”，可设0–5000，默认0。修改后点击“保存提前量”，下一轮播放生效，无需重新分离或截取PCM。1500表示原始开始10秒的人声在伴奏播放到8.5秒时发送，以补偿Vidu回传延迟；伴奏不延迟、不变速。最早从0秒发送，开头不足提前量时可能补偿不足。PCM提前量与歌词文字提前量独立，均以伴奏播放进度为基准。积压超过500毫秒、播放停滞或打断会停止旧PCM。分离模型首次使用自动下载，推理进程结束后释放GPU；分离质量及实际音画同步仍需试听。[分离与下行验证](docs/song-stems-validation.md)。

OBS歌词显示统一设置于“唱歌模块 → 已有歌曲导播 → 编辑 → 歌词文字提前量（毫秒）”，默认1500，范围-10000–10000。-1500表示PCM计划发送前1500毫秒显示，0表示发送后立即显示，1500表示PCM实际发送后1500毫秒显示；“PCM发送后显示歌词”输入已移除，不叠加第二个偏移。点击“保存提前量”后下一轮生效，已入队也可修改。负值以PCM计划发送时刻为基准，最早从0秒显示；非负值从每句首帧PCM写入成功开始计时。时间轴同时预览OBS显示和结束时刻；播放时显示“上一句＋当前句＋下一句”，当前句在中间突出显示。歌曲换句直接更新三行，不额外等待字幕淡出或淡入动画。[前四分之一歌曲的实际时序校准](docs/song-quarter-sync-validation.md)。

## 检查与打包

```powershell
npm run build
npm test
cargo test --manifest-path src-tauri/Cargo.toml
npm run package:win
```

安装包位于 src-tauri/target/release/bundle/nsis。首次使用仍需安装 WSL2 语音运行环境与模型；模型不打入安装包。
