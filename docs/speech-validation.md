## JSON 口播故障回归

用户保存的自定义人设要求返回 emotion / speech / segments 对象。原流式切句直接把 JSON 按换行送入 TTS，首行 emotion 也被当成台词。现已增加独立口播适配器：纯文本继续逐句流式；结构化回复完整解析后只取台词，截断或缺失台词时拒绝。人设与说话风格保留，输出格式由口播层约束。TTS 入口也拒绝结构化字段。

使用本机已保存的 deepseek-flash 配置，直接执行原生 sentences → synthesize 管道，输入“小宇：姐姐你有男朋友吗？”。真实输出为“哎呀，小宇你这一上来就问这么直接呀。姐姐现在主要还是陪着你们聊天啦，别急别急。”，分2句合成6.6秒PCM，总耗时约2.78秒。测试没有请求 Vidu，没有把测试声音自动送入直播。

另连续20次正常中文台词合成全部成功；3种 JSON / 结构字段输入被拒绝。新增回归覆盖完整 JSON 提取、截断 JSON、元数据对象、代码块、Unicode转义、思考过程隔离和正常首句流式。当前197项前端、68项Rust、7项Python测试通过；真实 DeepSeek / TTS 测试单独通过。常规Rust检查中另有3项本机集成测试保持忽略（含本次已手动执行的真实链路测试）。试听产物为 `.build-tmp/deepseek-omnivoice-reply.wav`。

原先的通用 Invalid or oversized TTS waveform 错误不足以判断是空波形、超长还是数值异常，现已分别报告；本次正常台词回归未复现该波形错误。未自动重播原失败槽位，避免重复播报已经部分提交的内容。

## 槽位动作发送回归

排查时的信令日志显示，槽位与承接动作写出了 type=97，但没有对应的 type=9。组件版文档区分了97的底层动作提示词与9的动作驱动文本。现统一在同一会话锁内排入97和9，等待两条 WebSocket 写入结果后才标记“已发送”；未就绪、写入失败、超时或取消均明确返回错误。日志将动作驱动与麦克风输入分开标识，并保留任务 msg_id。

移除了仅以关键字决定是否规划动作的筛选，所有弹幕均进行意图判断；已识别为动作请求却缺少描述时显示失败，防止悄悄只播台词。礼物保留固定手势。当前 DeepSeek Flash 的实时请求显式关闭默认思考，结构化规划预算增加到1024 token；实测中曾出现的空规划结果在修正后未复现。

使用本机已保存的 deepseek-flash 配置实测：札一下马尾、涂一下口红、笑一下均返回 action_request 及具体动作描述；你会扎马尾吗、姐姐你有男朋友吗均返回 question 与默认看向镜头。五条全部通过。真实 DeepSeek → TTS 管道另复测通过，生成5秒PCM。

本地200项前端、74项Rust测试通过；新增测试核验槽位/礼物/承接动作的97→9顺序、相同任务标识、双写入等待、失败传播及取消。常规Rust运行有4项本机集成测试忽略，其中动作意图与口播管道已单独执行通过。本次未创建收费Vidu会话，也未通过真实画面确认渲染动作，不能将本地写入确认视为服务端动作完成回执。

## 槽位回答与 PCM 提前准备回归

原队列仅提前准备动作与提问，实际回答在轮到播报时生成；播放泵在等待整段音频提交时也阻塞了后续准备。现将后台准备与播放泵独立，最多同时准备两条回答；TTS 空闲时串行预合成，缓存完整回答的句子 PCM，轮到槽位才发送动作和缓存。界面提前显示回答及声音状态，提前准备不会产生实际播报台词或完成事件。

206项前端测试、78项Rust测试通过，前端与桌面Rust构建通过。新增回归覆盖：首槽位发送尚未完成时六个回答继续生成且下一条声音开始准备；TTS忙时只重试合成、不重跑模型；跳过和重新生成释放缓存；迟到结果不能写回新任务或新会话；修改音色保留回答但重新合成；恢复持久化快照不复用PCM句柄；旧窗口清理不能删除新窗口缓存；取出缓存后实际音频通道正常结束。常规Rust检查另有5项本机集成测试忽略，其中本次PCM缓存探针已单独执行。

使用当前本机OmniVoice和已保存克隆参考实测“我叫晚晚，是直播间陪你聊天的姐姐。”：854毫秒完成预合成，返回136320字节裸PCM（24kHz单声道s16le，2.84秒），随后经缓存一次性取出并送入音频通道，耗时不足1毫秒，无第二次TTS请求。产物为 `.build-tmp/slot2-prefetched.wav`。真实DeepSeek→OmniVoice管道亦已在本次重构后通过，生成两句、8.15秒PCM；未创建Vidu会话，以上不包含线上数字人实际播放验证。

## FunASR 下行结尾确认

组件队列默认启用实际下行识别；全部PCM写入结束后，以完整回答的结尾匹配和末尾3字核验判断结束，不再固定等待1500毫秒或1200毫秒静音。匹配阈值统一使用播报结束匹配度（默认70%，可配50–100%），承接动作在确认后按其方向、角度和等待时间执行。

212项前端测试与前端构建通过。新增覆盖已通过阈值但遗漏最后3字不能完成、同音字与短回答、第一句匹配不能结束完整回答、PCM尚在发送不能完成、发送前采集的迟到识别不能完成、其他槽位与采集结果丢弃、断流/媒体过期拒绝、ASR错误保留人工确认，以及发送完成后不清空缓存而补充结尾识别。原未启用识别的静音兼容逻辑仍通过。

离线音频实测：将前述真实克隆PCM转换为16kHz，通过实际本机 /api/stt 识别为“我叫婉婉，是直播间陪你聊天的姐姐。”，FunASR推理1137毫秒，末尾10字匹配100%、最后3字确认。将该实际识别结果送入队列状态机，立即归档 played，无固定静音延时。该探针使用本机音频模拟下行输入，未连接Vidu RTC，不能替代线上实际播放验证。

承接动作专项复核：84项队列测试、3项原生动作发送测试通过。新增组件版完整链路回归，覆盖下一槽位PCM已缓存时，FunASR结尾确认只触发一次承接动作，重复识别和媒体回调不能重复发送，等待从动作写入确认后起算，分别验证0、1250、3000毫秒等待期结束才发送下一槽位PCM，旧槽位迟到识别不能再次触发承接。方向right_down与35度参数正确传递。现有关闭/跳过/换会话、动作失败、持久化失败和中断回归均通过。本次无需修改承接生产逻辑，也未通过Vidu真实画面核验动作完成时刻；已提交仍只代表两条WS信令写入成功。

## 承接移入下一槽位与回复动作延迟

后续按新要求修改为：每个组件槽位先提交自己的承接动作，确认写入即开始缓存PCM；回复动作在首帧PCM实际写入成功后延迟N毫秒提交，0为立即，500为延后500毫秒。原上一槽位结束后的承接等待不再作用于组件流程。配置持久化，当前槽位冻结配置，修改只更新待播槽位。

214项前端、81项Rust测试通过，另有5项本机集成测试保持忽略。新增原生回归确认首帧尚未写入时不计时、0毫秒与500毫秒触发、PCM结束或没有首帧时取消尚未触发的动作，以及承接和回复动作都绑定新槽位ID、非法延迟在播放前拒绝。新增队列回归验证FunASR结尾确认后同一时间即启动下一缓存槽位、不执行旧3000毫秒承接间隔、当前槽位冻结500毫秒而下一槽位采用新配置0毫秒、旧播放实例动作回调被丢弃。没有创建Vidu收费会话，实际动作画面与渲染时序仍需在线验证。

## OBS窗口原曲静音修复

歌曲应由OBS窗口本地播放完整原曲，分段PCM只用于Vidu口型，RTC远端音频维持静音。复核发现此前统一将asset原曲接入MediaElementAudioSourceNode，却没有在加载src前启用CORS；该节点对CORS-cross-origin资源须输出静音（[Web Audio规范](https://www.w3.org/TR/webaudio/#MediaElementAudioSourceNode-security)）。Tauri当前asset协议实现已提供窗口来源的允许跨域响应头。

现修正为先设置crossOrigin=anonymous与原曲muted=false/volume=1，再加载src；默认0提前量直接使用HTML媒体播放，不创建Web Audio通路。非零提前量保留延迟通路和完整尾音。227项前端测试、前端构建通过，新增回归核验加载前的跨域/音量设置，以及0提前量在Web Audio不可用时仍能启动原曲和PCM发送。

真实Edge Headless使用生产SongAudioBridge及与asset同样跨域响应头的本地WAV验证：旧路径播放时间前进到0.293秒，但声音RMS为0；修复后0毫秒与500毫秒均测得约0.216的非零声音RMS，并分别发送17、44帧PCM，无错误。0提前量未创建音频上下文，500毫秒创建一个延迟通路。探针禁用了浏览器系统声音，验证解码和音频输出数据，不创建Vidu会话，也未验证OBS Studio实际采集或线上视频口型。
