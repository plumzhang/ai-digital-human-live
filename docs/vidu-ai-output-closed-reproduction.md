# Vidu 同会话再次播报断开：真实接口复现记录

测试日期：2026-10-21，以下时间均为北京时间（UTC+8）。

## 结论

使用用户授权的本机已保存 Vidu API Key、原形象和豆包 Sophie 音色，复现了第一轮正常播完、空闲后再次播报时收到 `type=6 / ai_output_closed` 的问题。

绕过第二次“导入 3 条并开始测试”及其队列状态切换，直接发送一个合法 `type=100 / text_tts` 也出现同样的断开。因此，问题可以在没有第二次导入操作的情况下复现；证据指向 Vidu 对同一会话空闲后恢复原文播报的处理链路。具体是哪个内部模型或连接关闭，公开接口和客户端日志无法确定，需平台按 trace_id 检索。

之前增加新批次静音确认的修改没有解决该问题，不应作为已经修复的依据。

## 测试方式

- 创建真实 `vidu-s2` 视频会话，`voice_model.provider=doubao`，音色 `zh_female_sophie_uranus_bigtts`，使用本机保存的形象及会话人设。
- 通过真实 AliRTC SDK 7.3.7 入会，订阅远端音视频；不采集本地麦克风或摄像头。
- 使用项目中的 `InteractionQueue` 和 `monitorDownlinkAudio`，由真实下行 PCM VAD 判定每条播报结束。
- 使用预置中文口播答案排除模型生成差异。3 条均为普通弹幕，不提交礼物动作或承接动作。会话仍按应用设置开启动作能力。
- 对长间隔和直接播报对照，WS 每 10 秒发送 Ping，保持与桌面后端一致。
- 每条 text_tts 使用唯一 msg_id、连续 seq_id。断开前未收到 type=103 错误回执。
- 复现使用隔离的本地浏览器页面和真实接口，并非通过自动化点击现有 Tauri 窗口。页面复用项目实际队列和音频检测实现；第二组长间隔测试确实调用两次测试批次导入方法。

## 后续：自动恢复实现（2026-10-21）

已安装并阅读 [官方 vidu-s-api 技能](https://github.com/shengshu-ai/vidu-s-api/tree/main/skills/vidu-s-api)，安装位置为 `C:/Users/zhike/.codex/skills/vidu-s-api`。用户提供的 [Vidu API 文章](https://blog.csdn.net/Vidu_API/article/details/164582766) 将 `ai_output_closed` 归为 AI 输出通道异常，并建议重建会话。技能的 WebSocket 参考要求收到 type=6 后释放旧媒体，新会话使用新凭证。

本次新增故障后恢复流程，并未认定上述服务端空闲问题已消失：

1. 仅对本客户端创建会话的 `ai_output_closed` 自动恢复，停止旧会话调度与媒体回调。
2. 正在播报的任务记录为失败，原因明确注明完成情况未知，不重播；未播任务保留。
3. 查询旧会话，最多 10 次，确认 `ended` 后按原配置新建，使用新 live ID 和 RTC 凭证；状态未知或查询报错即停止。
4. 等待新控制连接、RTC 入会及实际播放画面后，恢复原先开启的自动队列。麦克风保持关闭。
5. 同一会话重复事件去重；10 分钟最多重建 3 次，按 1/2/4 秒退避。用户主动结束可取消恢复，在途请求返回的新会话会清理。
6. 后端结束事件携带 live ID，OBS 忽略旧会话迟到的结束通知，避免销毁恢复后的连接。

验证包括本地恢复状态机、队列中断及未播任务续播、旧 RTC 结束事件隔离、取消与限次测试、前端生产构建和 Rust 测试。本次未新增收费真实会话测试，自动重建后的实际恢复时长和连续直播表现仍待真实会话验证。
